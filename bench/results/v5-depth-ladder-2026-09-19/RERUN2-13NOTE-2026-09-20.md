**The pre-registration is not amended.** Every rule on `PREREGISTRATION.md` applies unchanged: the depth bands,

## Why

The 21-note and 30-note rungs ran on plugin build `b2c4548`; the published 13-note rung ran on `7c67c66`, before
`f2b3256`. That build gap was recorded as this ladder's standing limit. This run removes it.

**The plugin build is unchanged since `b2c4548`.** `git diff b2c4548..HEAD -- src/ package.json plugin/` is empty;
the two commits since are documentation. So these cells run the same build the 21/30 pair ran.

## Decided before the numbers exist

1. **The new measurement is the one that goes in the single-build ladder.** Not the lower of the two, not the one
   that looks more consistent with 285K and 389K.
2. **The published 13-note result stands.** It is not deleted, replaced or amended. It is what build `7c67c66`
   measured, and it keeps saying so.
3. **If the rung does not separate, that is the result and it gets published.** The three-point ladder claim in
   `HANDOFF.md` and the decision document would then be withdrawn to what survives, and the honest reading would
   be that the shallow end is not robust across runs.
4. **A cell is invalid on the pre-registered grounds only**: depth outside the 13-note band of 120,000–250,000,
   any priming prompt recorded `orchestrated`, or a non-zero exit. Rules applied by the same unedited
   `apply-rules.cjs`.

## The limit this run does NOT remove

It closes the **build** gap. It does not close the **run** gap.

Three rungs measured in two runs is still not one within-run curve. Rule 6 stands: each rung's percentage is read
against its own two arms and nothing else, and no percentage is differenced against another run's. What can be
said after this run is that three rungs were measured on one plugin build under one frozen config — which is
stronger than what exists now, and weaker than a single run of three rungs.
